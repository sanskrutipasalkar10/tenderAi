# Decision Log — Tender AI Platform

Add a row every time a technical choice is made. This is the difference between "I built
a tender-analysis pipeline" and "I chose X over Y because Z, measured how."

| # | Decision | Options considered | Chose | Why | Revisit if |
|---|---|---|---|---|---|
| 1 | Backend language | Python/FastAPI, Node/Fastify | Python/FastAPI | Confirmed with user; PyMuPDF/pdfplumber/Camelot are Python-native, keeps pipeline one language | Never without explicit new ask |
| 2 | Project tier | 1 / 2 / 3 | Tier 2 — Internal/Pilot | Internal bid-team users only; blast radius is "bad internal decision," not customer-facing | Pilot expands externally or multi-org |
| 3 | HITL mechanism | Full approve/override + correction table vs. citation-verification UI | Citation-verification UI | Every output already carries `page_ref` per spec's own success criteria; satisfies Tier 2's "if high-stakes" HITL requirement without new schema | Users start needing systematic correction feedback into prompts/evals |
| 4 | Architecture shape | Pipeline / single agent+tools / multi-agent | Pipeline (Celery map-reduce) | All stages deterministic and fixed; no runtime branching decision exists; not RAG, no retrieval loop to wrap in an agent | A future feature needs dynamic tool selection |

| 6 | Job orchestration | Celery+Redis / RQ+arq / FastAPI BackgroundTasks | Celery + Redis | Spec requires async per-chunk retries, not one long sync request; chord/group maps directly onto map(fan-out)→reduce(fan-in) | Pipeline complexity shrinks enough a simpler queue suffices |

| 17 | Reconciling colleague's DB schema | (a) adopt colleague's bronze/silver/gold schema as-is, accept page-*range* citations; (b) push back and ask colleague to add page-level granularity; (c) extend colleague's schema myself; (d) keep our exact-page schema as canonical and additionally populate colleague's 4 tables as a derived export/reporting layer | (d) — colleague's schema stays untouched/verbatim, our page-level schema (documents/pages/chunks/chunk_extractions/document_analysis/boilerplate_cache) remains the system of record; a sync step populates `company_master_profile`/`tender_bronze_raw`/`tender_silver_extracted`/`tender_gold_analysis` from it | Colleague's schema only tracks a `page_range` string per chunk (e.g. "Pages 1-20") — no way to cite one exact page. Colleague's schema also has no documents-lifecycle table, no dedupe cache, and no dedicated synopsis field. User chose to keep both: full fidelity internally, org-compatible export externally. Mapping detail: `docs/ARCHITECTURE.md` §Bronze/Silver/Gold export layer | Colleague's schema gains page-level granularity of its own — the export layer could then become the single schema |

Faking the DB layer honestly, rather than skipping these tests, still catches real bugs in the orchestration logic and the real extraction functions | Colleague's Postgres credentials arrive — add tests/integration/ tests against the real DB before Phase 2 is considered fully closed |
| 20 | S3 client `endpoint_url` handling | Always pass `settings.s3_endpoint_url` vs. omit when falsy | Omit when falsy (`get_s3_client()` only sets `endpoint_url` if configured) | moto's `mock_aws` only intercepts AWS's own default endpoints — a custom endpoint_url (MinIO-style) bypasses its interception and tries a real network call.
